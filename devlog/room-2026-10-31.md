# 2.5D 房间（Room）技术调研报告 — 2026-10-31

> 归属模块：`room-anime`（占位包，本文只做调研，不落地实现）
> 结论先行：**不要上真 3D，不要上 Live2D 商业 SDK 起步**。走「2D 立绘分层 + 伪 3D 场景（视差/景深/Y 排序）+ 有限 WebGL（PixiJS）」，以 DSH 客户端插件的全屏/右栏面板作为主容器，数据由 `bridge-core` 的事件流驱动。先做静帧房间原型，再补状态机与交互。

## 1. 需求拆解

小肥鱼房间要同时满足三件事，这三件事互相拉扯，选型必须同时看：

| 维度 | 具体要求 | 直接后果 |
| --- | --- | --- |
| 表现力 | 二次元角色 + 场景氛围（夜晚/台灯/雨声），2.5D 而不是纯平面 | 需要**分层 + 视差 + 光照叠加**，不是一张大图 |
| 状态感知 | idle / 听（麦克风）/ 说（TTS 播放）/ 摸鱼 / 睡觉 / 被戳 | 需要**状态机 + 动画轨道**，且能被 bridge-core 事件驱动 |
| 集成成本 | 要挂在 DSH 里，和 `console-web` 同一个 Web 面板体系 | 容器尺寸≈视口 45%~全屏，**不要独立 Electron 壳起步** |

真正的 2.5D 体验来自四件事，和引擎关系不大：
1. **分层**：bg / mid（家具）/ char（角色）/ fore（前景遮挡物）/ fx（粒子、光斑）五层，角色可被前景挡住 → 立刻有纵深。
2. **视差**：鼠标或窗口倾斜驱动层间位移，靠近的层位移大。
3. **Y 排序 + 透视缩放**：房间地面按 y 轴做线性缩放/投影，角色走动时大小与影长变化。
4. **光照统一**：一层 `screen`/`overlay` 混合的夜色蒙版 + 台灯径向渐变，所有资源色调被"搓"到同一张图里。

## 2. 候选技术栈横评

| 方案 | 代表 | 优点 | 风险/坑 | 适配小肥鱼 |
| --- | --- | --- | --- | --- |
| A. DOM/CSS 分层（推荐起步） | 纯 HTML + `transform: translate3d` + CSS 动画 | 零依赖、接入 DSH 面板最容易、改起来快、资源就是 png/webp | 动效由 CSS 关键帧驱动，复杂动作拼接弱；粒子/光效要靠额外 canvas | ★★★★★ 第一版 |
| B. PixiJS（2D WebGL） | pixi.js v8 + `@pixi/filter-*` | 渲染性能好、滤镜（blur/glow/shockwave）现成、分层容器天然 | 需要自己写状态机与补间；与 DSH 既有 canvas 抢 context 的概率低但存在 | ★★★★ 正式版 |
| C. Three.js / React Three Fiber | R3F + drei + zustand + gsap | 真 3D 房间、镜头语言强、社区范例多 | 美术要从 0 做 3D 资产（成本是 2D 的 5~10 倍）；移动端/低端机掉帧；DSH 里塞 WebGL canvas 需要处理尺寸与 DPR | ★★ 仅当要转视角/多人房间 |
| D. Live2D（Cubism SDK for Web） | Cubism 5 SDK | 表情/口型/视线最自然，可直接驱动 TTS 口型 | **商业授权**（年营收门槛，个人免费但需遵守条款）；模型制作要专门工具；web 版体积 ~2MB+ 模型 | ★★★ 角色表现力天花板 |
| E. 帧动画（sprite sheet / Spritesheet JSON） | TexturePacker + Pixi AnimatedSprite | 最接近 `dsh-anime25d-pets` 的形态，成本低、可批量 | 动作要人画/合成；口型只能做 3~5 帧近似 | ★★★★ 与 A/B 组合 |

**选型建议**：A（壳 + 分层 + 视差）→ B（PixiJS 接管渲染）→ E（帧动画补动作）→ 想要口型/表情再加 D。这条路径每一步都能独立交付，不会推倒重来。

## 3. 参考实现与可借鉴点

- **`@gestaltrun/dsh-pet` / `dsh-anime25d-pets`**：DSH 生态里的帧动画桌宠形态，包内声明 `frames2d` 与可选的 gameplay 块（状态条/衰减属性）。可借鉴的是**包结构**：立绘资源 + 状态机配置 + 交互热点全部随包分发，运行时只做调度，不做美术。小肥鱼房间应沿用这个思路：`room-anime/packs/<角色>/room.json` 描述层、锚点、动画、热点。
- **Tauri 桌宠类**（如 anime-desktop-pet 一类的透明置顶窗口）：能拿到"永远在最上层 + 透明背景 + 点击穿透"三件套，但 Windows 上是 `WS_EX_LAYERED` + 逐帧位图更新，硬件加速与透明窗口冲突（要么掉到 CPU 合成，要么闪烁）。**这是"独立桌宠壳"路线的核心坑**，也是本报告建议先挂 DSH 面板、暂不做桌面壳的原因。
- **Web 端 3D 房间范例**（R3F + Zustand + GSAP 的房间 demo）：可借鉴的是**相机与交互**：固定俯仰角的斜 45° 镜头、屏幕坐标 → 地面坐标的射线投影、点击地面让角色走过去。若走 A/B 路线，这套坐标换算用纯数学实现即可（等比投影 + y 排序），不需要引擎。
- **spine / DragonBones**：如果美术能出骨骼动画，比帧动画更省体积；但引入运行时和工具链，且 web 端对 DSH 的加载器要求更多。**不在第一版范围。**

## 4. 推荐架构（与 bridge-core / console-web 的关系）

```
bridge-core (Python)                DSH Host (Node)                 Browser (client plugin)
  微信收发 / ASR / TTS   ──WS/HTTP──▶  console-web host 路由  ──fetch/SSE──▶  room-anime UI
  事件: user_msg / asr / tts_start / tts_end / mood_change              │
                                                                        ├─ RoomStore (zustand 或 轻量 emitter)
                                                                        ├─ CharacterFSM: idle→listen→think→speak→sleep
                                                                        └─ Renderer: DOM 分层 → PixiJS
```

关键设计：
1. **房间只消费事件，不发命令**。所有状态变化来自 bridge 事件（`asr.final`、`tts.start/end`、`reply.ready`、定时器），保证"看到的就是真实运行状态"。
2. **口型用 TTS 时长近似**：`tts.start` 带 `duration_ms` 与文本，房间按字数/时长切 3 帧口型 + 眨眼随机，不做真实音频分析（成本/收益不划算）。
3. **FSM 分层**：情绪层（mood: 平静/开心/害羞/生气，慢变）+ 动作层（idle/listen/speak/sleep，快变）。两层组合出动画与表情，避免状态爆炸。
4. **资源规范**：1920×1080 设计稿，立绘 2x 导出 webp，单角色 ≤8MB；层命名为 `00-bg / 10-mid / 20-char / 30-fore / 40-fx`，锚点写在 `room.json`。
5. **性能**：`requestAnimationFrame` 单循环，鼠标移动/视差用 CSS 变量（`--parallax-x`）避免 React 重渲染；粒子走 canvas 单层，不每个粒子一个 DOM。

## 5. 实现路径（分四步，每步可交付）

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| M0 静帧 | 分层图片 + 视差 + 夜色蒙版，`room.json` 驱动 | 浏览器打开即见房间，鼠标移动有景深 |
| M1 状态 | FSM + 帧动画（idle/眨眼/说话），接 bridge 事件 | 微信来消息→角色抬头；TTS 播放→口型+字幕 |
| M2 交互 | 点击热点（头/手/台灯），拖拽视差，Y 排序走动 | 摸头有反应，关台灯变暗 |
| M3 养成 | 好感度/心情持久化（写回 bridge-core config），夜间模式 | 跨会话状态一致 |

## 6. 可行性与坑（按严重度排序）

1. **面板尺寸受限**：DSH 右栏宽度=视口 45%、上限 70%，宽度不足时框架会先压到 300px 再让占用方关闭。房间只适合**全局面板（`main` keyed slot）+ 全屏 or 竖屏版式**，不要指望右栏。→ 设计两套版式（16:9 与 9:16），按容器尺寸切换。
2. **WebGL 资源竞争**：DSH Web 已有大量 DOM/动画，PixiJS 占一个 canvas 尚可，但若同时开多个房间实例会掉帧。→ 单实例 + 页面隐藏时 `document.hidden` 暂停渲染。
3. **透明桌面壳**（若将来做）：Windows 分层窗口 + 硬件加速的冲突、多显示器 DPI、全屏游戏上方捕获鼠标。→ 保持"面板优先"，桌面壳只在用户明确要求时做，且用 Tauri 的 `transparent: true` + 关闭 GPU 合成兜底。
4. **Live2D 授权与体积**：Cubism SDK 有营收门槛条款，模型 2MB~10MB，加载器与 DSH bundle 的 ESM 兼容要额外处理。→ 第一版避开。
5. **口型同步**：真实 lip-sync 需要音素对齐（轻量方案：对 TTS 文本做拼音切分 + 时长均摊）。**不要**上音频 FFT 分析，收益低。
6. **美术成本才是主成本**：2.5D 房间的成败在资产（分层、光影、动作帧），不在代码。→ 先做"一套通用房间 + 一个角色"的模板，后续角色只换素材。

## 7. 结论

- 技术栈：**PixiJS v8 + 自研轻量 FSM + 分层 webp + JSON 配置**，第一版用 DOM/CSS 起步；Three.js/R3F 仅在"要自由镜头/多人房间"时考虑；Live2D 等有明确变现或用户强需求再评估授权。
- 架构：room-anime 只做渲染与状态呈现，事件来自 bridge-core，通过 console-web host 路由转发，**不直接连微信桥**。
- 节奏：先做 M0 静帧（1~2 天，纯前端可离线验证），等 voice/console-web 稳定后再动 M1。
